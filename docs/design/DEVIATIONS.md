
## Frontend (messaging-console) deviations / assumptions
- Payloads for endpoints CONTRACT section 5 lists but does not detail (ops summary/queues, providers, bulk jobs, template detail/versions, audit/delivery events, history entries, dead letters, failed messages, preferences, template preview) use the shapes in `frontend/messaging-console/src/app/core/models/api.models.ts`; reconcile with the OpenAPI spec when the backend lands.
- `POST /dev/token` is called with roles WITHOUT the ROLE_ prefix (matches backend `Roles` constants), the sender persona requests scope `messages:bulk`, and the UI accepts both `access_token/expires_in` and Jackson-default `accessToken/expiresIn` response names; it also accepts ROLE_-prefixed roles when decoding the JWT.
- `GET /api/v1/me` is not called (roles/tenant are read from the dev JWT for UX gating only); `GET /api/v1/diagnostics/messages/{id}` is not surfaced in the UI because raw provider payloads could contain content.
- Fonts/icons are not loaded from a CDN (system font stack, text-only controls) so builds work offline.
- `frontend/mock-api/server.mjs` is an opt-in UI-development stub, not an application backend.

## Backend foundation (stage 1) deviations / additions
- Additive error code `DUPLICATE_RESOURCE` (HTTP 409) for unique-constraint style conflicts (duplicate template code+channel, duplicate template locale version, data-integrity fallback). CONTRACT 5 lists no code for these; `CONFLICT_OPTIMISTIC_LOCK` would be misleading. It is part of the committed OpenAPI `ErrorCode` enum.
- Policy rejections at submission (opt-out, suppression, deleted recipient, no address, expiry before a deferred send) are persisted as `REJECTED` messages (ACCEPTED -> REJECTED, audited) and answered `202` with `status=REJECTED` and `statusReason`, rather than a 4xx. This keeps the idempotent replay and audit trail consistent. `POLICY_SUPPRESSED` is therefore not returned by stage 1; stage 2 may use it for dispatch-time rejections surfaced via other paths.
- `ProviderOutcome` lives in package `provider` (as requested for stage 1), not `domain` as CONTRACT 3.2 groups it; `MessageAttempt` imports it from there.
- New package `coordination` (CoordinationService, InMemoryCoordination, RedisCoordination, ResilientCoordination, RateLimitDecision) for the Redis ports required by CONTRACT 1; CONTRACT 2 does not list it.
- Additional message_request columns beyond the CONTRACT 4 list (CONTRACT says "..."): `client_reference`, `options_json`, `metadata_json`, `fallback_channels`, `fallback_index`, `locked_until`, `dlq_reason`, `discarded`, `status_changed_at`. Additional columns: `provider_config.version`, `message_attempt.state` (STARTED/FINISHED), `outbox_event.available_at` (lets scheduled/deferred messages sit in the outbox until due; the publisher selects `status=NEW AND available_at <= now`), `bulk_job.template_code/channel/category`.
- Requeue/replay is implemented as: CAS status FAILED|DEAD_LETTERED -> QUEUED plus an outbox event (attemptNo = attemptCount + 1, available immediately). The outbox publisher must therefore publish regardless of whether the message is already QUEUED, and must only CAS VALIDATED -> QUEUED (never fail when it is already QUEUED). Cancelled messages are skipped by the publisher (status != VALIDATED/QUEUED).
- A template version's `created_by` is overwritten with the editor on edit (author of record), so four-eyes approval cannot be bypassed by having a second person edit a draft.
- `application-*.yml` has no default profile on purpose (secure by default: a forgotten profile must not enable the dev token issuer). Run with `--spring.profiles.active=local`.
- The committed OpenAPI contract test treats the stage-2 prefixes (`/api/v1/providers`, `/ops`, `/bulk-jobs`, `/callbacks`, `/diagnostics`) and `/dev/**` as "documented, not yet served"; stage 2 must delete `STAGE_2_PREFIXES` from `OpenApiContractIT` so that the full committed spec is enforced.

## Backend stage 2 (messaging core) deviations / additions
Append-only record for the dispatch pipeline, callbacks, providers and ops APIs. Spring Batch (`batch/`, bulk-jobs controller, retention job) is built separately and is not covered here.

### Interface and shared-code changes other code must know about
- `DispatchHandler` gained a default method `onPoison(envelope, deliveryCount, cause)`: the bus calls it after it dead-lettered an envelope on its own (poison threshold or unreadable body) so `DispatchConsumer` can mirror that in the database. Existing lambdas keep compiling.
- `MessagingMetrics`: new gauge `messaging.queue.oldest.age` (seconds, bound in `bindQueueStats`), `publishPercentiles(0.5, 0.95, 0.99)` on `messaging.provider.latency` and `messaging.dispatch.delay` (used for the p95 values of `/providers` and `/ops/summary`), and strong references to the suppliers handed to `bindQueueStats` / `bindCircuitState` (Micrometer holds gauge state weakly; without this the gauges turned into NaN after a GC).
- `NotificationService.requeueInternal` (operator requeue and replay) now sets `max_attempts = attempt_count + messaging.dispatch.max-attempts`: a replayed message gets a fresh attempt budget, otherwise it would be exhausted again by its first failure.
- `MessageDtos.MessageSummary` gained `channelUsed`, `templateCode`, `nextAttemptAt` (additive; the Angular console already reads them).
- Repositories gained queries: `MessageRequestRepository.markClaimed/setNextAttemptAt/applyFallback/setMaxAttempts/countByChannelSince*`, `MessageAttemptRepository.findFirstBy...`, `OutboxEventRepository.countByStatusAndAvailableAtLessThanEqual/existsByAggregateIdAndStatus`, `AuditEventRepository.countBy.../findFirstBy...` (reconciliation bookkeeping). New migration `V50__dispatch_indexes.sql` adds the indexes these queries need (also appended to `db/oracle/oracle_core_schema.sql`).
- `GlobalExceptionHandler`: database connection failures (`DataAccessResourceFailureException`, `CannotCreateTransactionException`, `TransientDataAccessException`, JDBC connection exceptions in the cause chain) answer `503 SERVICE_UNAVAILABLE` + `Retry-After: 5` instead of 500 (fail closed, clients retry with the same idempotency key). `MessageController.submit` calls `BackpressureGuard.check()` first (503 + `Retry-After` when bus depth + due outbox rows reach `messaging.backpressure.max-queue-depth`).
- Configuration: the new keys live in two extra records instead of `MessagingProperties` (to avoid touching a file the batch module also edits): `messaging.pipeline.*` (`PipelineProperties`: auto-start, shutdown-timeout, requeue delays, replay-window, `scheduler.*`, `resilience.*`) and `messaging.simulator.*` (`SimulatorProperties`). `application-test.yml` sets `messaging.pipeline.auto-start=false` and `scheduler.enabled=false` so stage-1 tests that drive the lifecycle by hand are not disturbed; `AbstractPipelineIT` switches both on. `application.yml` defines the profile group `prod-like -> rabbit` (the Rabbit bus and topology are `@Profile("rabbit")`). Percentile histograms are also enabled for `messaging.dispatch.delay` and `messaging.provider.latency`.
- `backend/pom.xml`: `**/*ContainerIT.java` is excluded from test compilation in the default build (the Testcontainers dependencies exist only in profile `containers`); the profile re-includes it. `scripts/it.sh` is a fast loop for single failsafe tests.
- `ProviderAdminService` lives in package `provider` (not `service`) because it knows the simulator classes; `service`, `messaging`, `scheduler`, `callback` and `domain` never name a concrete provider (checked by `NewProviderWithoutOrchestrationChangeTest`).

### Behaviour that differs from CONTRACT section 6 / the flow documents (and why)
1. Consumer order: cancel/status, expiry, policy, provider selection, circuit state and the provider token bucket are checked **before** the claim; the claim is then ONE transaction (unique `processed_message` row + CAS QUEUED to PROCESSING + `locked_until` + `attempt_count` + attempt row `STARTED`). Reason: a requeue because of the rate limiter reuses the same `dispatchId` and must not be blocked by the dedupe table, and must not consume an attempt. Expiry and dispatch-time REJECTED claim first and then move PROCESSING to FAILED(`EXPIRED`) / REJECTED because the state table has no QUEUED to REJECTED/FAILED.
2. Quiet hours met at dispatch time defer through the outbox (new outbox row with `available_at` = end of the window, message stays QUEUED); there is no QUEUED to VALIDATED transition.
3. The outbox publisher claims the row (`markSent` CAS), moves VALIDATED to QUEUED and publishes inside one transaction: a failed publish (backpressure, broker down) rolls everything back, giving at-least-once delivery. An envelope can overtake the commit, so the consumer requeues a message that is still VALIDATED for 150 ms (at most 40 deliveries, then dead-letter).
4. Multi-step outcomes use consecutive, individually legal transitions in one transaction: fallback after PERMANENT_FAILURE is PROCESSING to FAILED to QUEUED; fallback or dead letter after exhausted retries is PROCESSING to RETRY_PENDING to QUEUED / DEAD_LETTERED; reconciliation "not received" is DELIVERY_UNKNOWN to FAILED to QUEUED; mirroring a poison message is QUEUED to PROCESSING to FAILED to DEAD_LETTERED. The state table (and `MessageStateMachineTest`) are unchanged. Fallback gives the new channel a fresh attempt budget and uses a new idempotency reference group (`messageId:2`, ...).
5. The circuit-breaker permit is **reserved before the claim** (`ResilientProviderInvoker.acquire`, released again if the message is not claimed, rate-limited or fails to render): an open circuit or exhausted half-open probes requeue the delivery (0.1 to 5 s, no attempt consumed, as in ADR-0006), so a recovering provider never burns the attempt budget of messages that merely met a refusing breaker. `invoke(provider, request)` without a reservation still returns TRANSIENT `CIRCUIT_OPEN` without touching the provider (used by callers that do not reserve). The breaker leaves OPEN by itself (`automaticTransitionFromOpenToHalfOpenEnabled`), otherwise the state pre-check would keep it open forever.
6. PUSH timeouts/ambiguous answers are retried like transient failures (the provider deduplicates on the idempotency reference); EMAIL/SMS go to DELIVERY_UNKNOWN. The provider token bucket uses `burst = rate`.
7. Callbacks: a replayed `X-Event-Id` is answered `200 {"result":"replayed"}` (not 409 `REPLAYED_EVENT`, which stays unused); an unknown provider, a key not bound to the provider (`provider_config.hmac_key_ref`, or `<ref>-next`) and every signature problem give the same `401 INVALID_SIGNATURE`; an event for an unknown message is `202 unknown_message` and is neither stored (`delivery_event.message_id` is a mandatory foreign key) nor remembered by the replay guard; `delivery_event` has a unique `(provider_id, provider_event_id)`, so a duplicate creates no second row (the callback-flow text about recording a DUPLICATE row cannot be done with that constraint); extra result tags `conflict`, `unknown_message`, `malformed`. `callback-flow.md` and `specs/0002-new-provider-adapter.md` still describe the earlier plan; `callbacks-normalization.md` is current. Acme's payload uses `id` for the event id (spec 0002 says `eid`) and the key id is `acme-sms-key` (seed `hmac_key_ref`; spec says `acme-key-1`).
8. Free-text provider reasons are never copied into audit or log lines (only code-like reasons); raw payloads go to Mongo redacted. The `replay_guard` table is not purged by this module: the retention job should delete rows older than `messaging.pipeline.replay-window`.
9. Reconciliation bookkeeping needs no new column: spacing and the `reconcile-max-checks` bound are derived from `RECONCILIATION_CHECK` audit events.
10. RabbitMQ: only the total ready count of the dispatch queue is available, so `GET /ops/queues` reports it under `NORMAL` (other priorities 0) when the Rabbit bus is active; delays are rounded up to the next TTL tier (5 s, 30 s, 2 m, 10 m) and delays above 10 m are finished with an `x-not-before` header. Rabbit code is NOT executed here (no broker): only `RabbitBusSupportTest` / `RabbitTopologyTest` (pure parts, topology vs `definitions.json`) run; `RabbitMessageBusContainerIT` compiles under `-Pcontainers` but was not run.
11. Simulators: PERMANENT mode answers `SIM_REJECTED` (no suppression); the address pattern `...+hardbounce@...` simulates a hard bounce (`HARD_BOUNCE`, adds a suppression). The simulator remembers the last request per idempotency reference in memory for tests (`lastRequest`). `POST /dev/simulator/callbacks/emit` answers 202 with `{"scheduled":[...]}`.

### OpenAPI / frontend reconciliation
- Backend serves the committed OpenAPI. Additive fields keep the Angular console working unchanged: `ProviderHealth.rateLimitPerSec` (= `ratePerSec`) and `faultProbability`; `ProviderConfigRequest` accepts `rateLimitPerSec` as an alias of `ratePerSec`; `QueueStats.oldestMessageAgeSeconds` and `consumersPaused`; `OpsSummary.total`; `MessageSummary.channelUsed/templateCode/nextAttemptAt`. The spec was extended for the callback responses (200 replay, 400, `result` values), the emitter response and descriptions; `docs/api/openapi.yaml` is the identical copy.
- **Frontend change still needed** (not edited here): `HistoryEntry` in `api.models.ts` expects `{at, kind, title, detail: string, status, actor}` but `GET /messages/{id}/history` returns the specified `TimelineEntry {at, kind, type, summary, detail: object}` (the actor is `detail.actor`, the target status `detail.to`). Map `summary` to the title, render `detail` as an object and drop `status/actor`.
- `OpenApiContractIT` no longer exempts providers, ops, callbacks and diagnostics; `/api/v1/bulk-jobs` stays exempt only because the bulk controller lives in the separately built batch module and is absent here.

### Test-support notes
- Pipeline tests (`AbstractPipelineIT`) run the real asynchronous pipeline with simulators, an adjustable clock (system time plus offset), a programmable `DispatchHook`, a failing-`DataSource` wrapper and a switchable coordination backend; every case retires leftovers of earlier cases, uses fresh recipients and zeroes the simulators. Raw JDBC writes into TIMESTAMP columns must use UTC `LocalDateTime` (see `utc(...)`) and TIME columns must be written through JPA, because Hibernate runs with `hibernate.jdbc.time_zone=UTC` while the JVM zone is not UTC.

## Bulk jobs and retention (batch module) deviations / additions
- Extra configuration, all with safe defaults (no change to the shared `application*.yml` needed): `messaging.bulk.{max-upload-bytes,max-line-length,max-columns,default-rate-per-second,max-rate-per-second,retry-limit,max-synthetic-rows,max-parallel-jobs,launch-queue-capacity,stale-after,sweep-interval,stop-wait,sweeper-enabled,delete-file-on-completion}` (record `batch/BulkProperties`) and `messaging.retention.{enabled,dry-run,batch-size,pause-ms,max-batches-per-table,processed-message-days,outbox-sent-days,replay-guard-hours,purge-bulk-files,cron}` (record `scheduler/RetentionProperties`). The core keys of CONTRACT 9 stay in `MessagingProperties`.
- Migration `V200__bulk_ledger_legal_hold.sql`: `bulk_job_row` (the `(job_id, external_ref)` ledger of CONTRACT 7, plus the line number), a unique index on `bulk_job_failure(job_id, line_no)`, a `legal_hold` table honoured by `RetentionJob` (scope TENANT or MESSAGE, active while `released_at IS NULL`) and age indexes for the purge queries. The Oracle reference DDL was not extended.
- OpenAPI additions (additive, not yet in `messaging-api-v1.yaml`): optional query parameter `createRecipients` (default true) on `POST /bulk-jobs/generate-synthetic`, optional `sort` on the two list endpoints, `Location` header on the 202 responses, and `bulk_job_failure.line_no = 0` meaning "job level failure" (e.g. `SKIP_LIMIT_EXCEEDED`, `STEP_FAILED: <exception type>`).
- Authorization: create, generate-synthetic, stop and restart need role SENDER, TENANT_ADMIN or PLATFORM_ADMIN **and** scope `messages:bulk` for every caller, PLATFORM_ADMIN included; a refusal is audited as `BULK_JOB_DENIED` and answered 403. Reads (list/get/failures) need one of SENDER, TENANT_ADMIN, PLATFORM_ADMIN, OPERATOR, AUDITOR and are tenant scoped (404 across tenants).
- Counting: `processed = succeeded + failed + duplicate`. Rows rejected by policy at submission (opt-out, suppression, ...) are persisted as `REJECTED` messages but counted as `failed` with reason `POLICY_REJECTED: <reason>`. Duplicates are filtered (not skipped), recorded in `bulk_job_failure` as `DUPLICATE_EXTERNAL_REF: first seen on line N`, and do not count against `skip-limit`. Status is `COMPLETED_WITH_ERRORS` iff `failed > 0`.
- Restart: with `messaging.bulk.concurrency = 1` the reader checkpoints per chunk and a restart resumes from the last committed chunk; with more workers no exact position exists, so the restart re-reads the file from the top and the ledger plus the idempotency key `bulk-<jobId>-<externalRef>` make already processed rows no-ops. With several workers which occurrence of a duplicated reference wins is not deterministic (exactly one is sent either way).
- Details of rows rejected inside a chunk that is rolled back (job failed) are not kept; the job-level failure row explains why it failed. A rolled back chunk leaves no counter and no message, by design.
- `generate-synthetic` creates the recipients it needs (`SYN-0000001...`, fictitious `example.test` addresses) for the caller's tenant and generates exactly the variable columns of the chosen template; `createRecipients=false` skips that and every row then fails with `RECIPIENT_NOT_FOUND`.
- Upload files live in `<messaging.bulk.upload-dir>/<tenant>/<jobId>.csv` (server generated name, normalised to UTF-8/LF, BOM and trailing blank lines removed), are deleted when the job completes (`delete-file-on-completion`) and otherwise by `RetentionJob` after `message-days`. Jobs run on the node that accepted the request (single-node assumption for stop/orphan recovery): `stop` on a RUNNING job whose batch execution is not alive in this JVM closes the orphaned execution as STOPPED so it can be restarted; the sweeper marks jobs without progress for `stale-after` as ABANDONED (terminal for the API).
- Extra meters (additive): `messaging.bulk.writers.active`, `messaging.retention.deleted{table}`, `messaging.retention.run{dryRun}`. Extra audit actions: `BULK_JOB_DENIED`, `BULK_JOB_ABANDONED`, `RETENTION_PURGE`.

## React operations console (additional frontend)
- The original brief said "no React"; the user later asked explicitly for a React console **in addition to** the Angular one, so that rule is superseded for `frontend-react/` only. The Angular app is untouched and stays the reference UI.
- `frontend-react/messaging-console-react` (React 19, TypeScript strict, Vite 7, React Router 7 with `React.lazy` routes, TanStack Query 5, Vitest + Testing Library + MSW) talks to the same backend and the same contract as the Angular console: models, error-code table, personas, role matrix, validators and the real-backend fixes of `docs/validation/integration-notes.md` were ported 1:1. Dev port 15200 (Angular: 14200), `API_PORT` honoured by `vite.config.ts`.
- **No UI library**: instead of MUI the console uses a small in-repo component set (`src/components`) and one hand-written stylesheet, so there is no third-party UI dependency, no web font and no CDN asset (the build works offline). Forms are plain controlled forms with the Angular validators ported to plain functions; React Hook Form and zod were not added (they would have duplicated the ported validators).
- Auth/session, the tenant-scope header and the loading counter are small external stores (`useSyncExternalStore`) instead of context providers; a 401 clears the session and the route guard redirects to `/login?reason=expired`.
- Differences against Angular that are deliberate: persona picker is a real list of buttons (the Angular one puts `role=listitem` on buttons); fallback channels on the submit form are checkboxes instead of a multi-select; quiet-hours/fallback inputs keep the Angular text format; the preferences page re-applies the user's edits after a conflict reload by laying them over the fresh record instead of patching the form.
- Not executed: Lighthouse/axe audits, Safari/Firefox, any run against Oracle/PostgreSQL-backed profiles (the live check used the `local` profile on H2).
